Milkdrop 2.0 introduced the ability to use pixel shaders (nowadays more frequently called fragment shaders) for both
the [Image Warp effect](../effects/image-warp) and final post-processing instead of the
classic [Post-Processing effects](../effects/post-processing-noshaders). Since Milkdrop was using DirectX for rendering,
HLSL was used to write shaders in presets.

If you're already familiar with shaders and GPU programming, you can skip the following section.

## Shader Concepts

Shaders, in general, are programs which execute inside the GPU instead of the CPU. A GPu is much more limited in what
kind of programs it can run, but is heavily optimized for massively parallel execution and fast memory access. Because
of this, shaders are generally small programs which work on a very specific task and only on small "problems" - like a
vertex or a single pixel.

### Fragment Shaders

Different uses require different shader programs, but in Milkdrop's case the only type we're interested in is the
fragment shader and will ignore the other types.

A fragment, or in classical terms a pixel shader, is a type of GPU program that has the purpose of calculating the color
of a single pixel (or "fragment"). Its only output is a single RGB color value - think of it as a function
`ReturnPixelColor(x, y)`, where `x` and `y` are the coordinates of the pixel in a range from 0 to 1. Since `x` and `y`
are often confused with 3D coordinates, shaders - including those used in Milkdrop presets - mostly use `u` and `v`
instead for pixel and texture coordinates.

### Input Values / Uniforms

In addition to the coordinates, shaders often have additional, fixed input values - called "uniforms" - like colors,
light
vectors and other values required to calculate the resulting image. Some of these values are identical for all pixel
shader invocations for a particular image. Other uniforms such as texture coordinates and vertex colors are interpolated
based on the position and geometry of the vertices making up the triangle the fragment shader is drawing.

Inside the shader, these values, regardless of their origin, _can_ be used to calculate the final output color. A shader
can, in theory, return a fixed, hard-coded color value, resulting in an image (or triangle) filled with that color.

It is also noteworthy that each shader program instance that runs on the GPU does not have access to any neighboring
pixels and their colors (as these might also still being calculated at the same time). The color value has to be derived
from only the available, fixed input values and math.

### Texture Sampling

The only external, flexible data source a shader has access to is textures. Textures bound to a shader program can be
sampled using `uv` coordinates, returning the color value of the texture at the specified location. When sampling a
texture, the filtering mode (pixel-exact or bilinear filtering) and the wrap mode (wrap, clamp) how colors are
interpolated and how the sampler behaves when using coordinates outside the \[0..1] range of the `u` and `v` components.

It is possible to sample multiple textures and also the same texture in any number of locations. This enabled
mixing/blending of multiple textures or creating a bilinear or bicubic scaling filter.

### Runtime Complexity

Remember a shader executes _once per pixel_ on a given image. This means that the same code is executed 8.294.400 times
on a 4K image - for every frame that is being rendered. Since each frame normally requires several steps to get
rendered, this number can generally be multiplied by a larger factor.

To keep frame rates high and presets running well even on less capable hardware, shaders should be well optimized and
kept as small as possible. Texture sampling and some math functions are highly expensive and should be used with
caution.

## Milkdrop Shader Types

A preset can contain two separate custom shaders:

1. The **warp** shader, which is applied early in the drawing process (with only
   the [Motion Vector effect](../effects/motion-vectors) being drawn before) and is used to warp, translate, rotate,
   zoom or otherwise manipulate the previous frame. Or even draw a completely new image.
2. The **composite** shader, which is rendered as the very last step before the image is displayed to the user. The
   composite shader output is also never passed on to the next frame and discarded, qualifying as a post-processing
   step.

Technically, both shaders use (mostly) the same inputs and could create the same output. The only difference is in the
position within the rendering process. There are some small technical differences in how the underlying geometry is set
up and drawn, but that has no huge impact on the actual drawing.

By combining both shaders, some interesting presets can be created. For example, the warp shader and the following
effects can draw three separate grayscale images into each RGB color channel, which the composite shader can then sample
to
calculate three different effects.

## Writing Milkdrop Shaders

Shaders in Milkdrop presets are only a part of the full shader that is compiled and sent to the GPU. Shaders in presets
only need to implement a part of the usual `main` function of the shader. All inputs and some boilerplate code will be
added by Milkdrop/projectM when loading the preset. Instead of the mentioned `main` (or rather `PSMain()` in HLSL)
function, presets use a special placeholder, `shader_body` and then put their main code inside of block brackets `{}`.
The return value - or output color - is pre-declared as `float3 ret` and assigned zeroes in all three components.

With this knowledge, a basic preset shader that simply returns the input texture as-is looks like this:

```hlsl
shader_body {
    ret = GetMain(uv);
}
```

The `GetMain()` function is one of the pre-defined functions Milkdrop shaders can use for convenience
to [sample specific built-in textures](built-in-textures).

To declare a function which can be called from the `shader_body` block, simply define it above as in any other HLSL
program:

```hlsl
float3 GetMainDecayed(float2 uv) {
    return GetMain(uv) * 0.98;
}

shader_body {
    ret = GetMainDecayed(uv);
}
```

### Basic HLSL Reference

HLSL provides a huge number of types, functions and features. To get started, here is a useful selection of the most
important ones.

#### Data Types

| Type                | Description                                                                                           |
|---------------------|-------------------------------------------------------------------------------------------------------|
| `float` or `float1` | A single floating-point scalar                                                                        |
| `float2`            | A vector of two floats, usually used for texture coordinates)                                         |
| `float3`            | A vector of three floats, often used for either RGB color values or 3D coordinates)                   |
| `float4`            | A vector of four floats (also called quaternion), mostly used for RGBA color values and Euler angles) |
| `float2x2`          | A 2x2 matrix, used for 2D rotation and/or scaling                                                     |
| `float3x2`          | A 3x2 matrix, used for 2D rotation, scaling and translation                                           |
| `float3x3`          | A 3x3 matrix, used for 3D rotation and/or scaling                                                     |
| `float4x3`          | A 4x3 matrix, used for 3D rotation, scaling and translation                                           |

Matrix types can be declared in any combination of rows and columns, with each count ranging from 1 to 4, inclusive.

The following data types are also available, and can have component numbers like the above examples to use them as
vectors or matrices:

| Type              | Description                                      |
|-------------------|--------------------------------------------------|
| `int`             | A signed 32-bit integer scalar                   |
| `uint` or `dword` | An unsigned 32-bit integer scalar                |
| `half`            | An half-precision 16-bit floating-point scalar   |
| `double`          | An double-precision 64-bit floating-point scalar |
| `bool`            | A boolean value, either `true` or `false`        |

Arrays of values can be declared and accessed using the `[]` operator, while the number inside the brackets determines
the array size when declaring a type and the zero-based index of the element when accessing it:

```hlsl
float myArray[4] = { 1.0, 2.0, 3.0, 4.0 };
float thirdElement = myArray[2]; // 3.0
```

It is not possible to create dynamically-sized arrays because the GPU does not have access to random memory and all
working data must be allocated directly on the execution stack.

The boolean operators do not short-circuit in HLSL as they usually do in other languages. This means that, regardless of
the value of the left operand, both sides are always evaluated.

#### Component Swizzling

In HLSL, vector components can be accessed using the `.` operator, followed by up to four components represented by the
letters `x`, `y`, `z` and `w` or their equivalents `r`, `g`, `b` and `a`, in order. The same component can be used
multiple times.

This is useful in a number of ways, most often to extract a subset of vector components into a smaller vector, e.g. a
float3 RGB color from a float4 RGBA vector:

```hlsl
float3 rgbColor = tex2D(sampler_mytex, uv).rgb; // tex2D returns a float4
float4 myVec = { 1.0, 2.0, 3.0, 4.0 };
float4 inverted = myVec.wzyx; // Now: { 4.0, 3.0, 2.0, 1.0 }
```

### Additional Information

- For best compatibility, make sure to only use HLSL syntax up to Shader Model 3.0.
- It is _not possible_ to use any other shading language such as GLSL to write preset shaders.
- Preset shaders cannot return an alpha value. The image is always drawn 100% opaque, replacing the previous image
  completely.
- It is not possible to use arbitrary _expression variables_, e.g. from the `per_frame` code, inside shaders.
  See [Shader Inputs](shader-inputs) for a list of available values which can be used in preset shaders.
- When changing color values, keep in mind that the preset texture uses an integer range from 0 to 255 for each color,
  even if the shader uses a 0 to 1 range. Output values will get rounded to the nearest integer, and thus, some very
  small adjustments like applying a `0.999` decay multiplicator, may simply get lost.

### Editing Shaders In .milk Files

It is highly recommended to use a dedicated preset editor, e.g. the built-in editor in Milkdrop, to write preset
shaders.

Preset files store shaders as a keyvalue pair for each line in the program, with the keys having a prefix of
either `warp_` or `comp_` and being continuously numbered beginning with 1. After the `=`, each _shader_ line is
prefixed with the \` character, followed by the actual shader code line. As a composite shader, the initial simple
example will look like this in a preset file:

```
comp_1=`shader_body {
comp_2=`    ret = GetMain(uv);
comp_3=`}
```

It is important that the key numbering is not interrupted, as Milkdrop/projectM will stop reading the shader lines on
the first missing number. Inserting a line at the beginning of a longer shader will require incrementing the indices of
_all following lines_.
